# OrbitHire Current Job-Ingestion Code Audit

## What job sources exist today, and how does data flow through the system?

### Takeaway
OrbitHire already has a substantial low-cost ingestion stack: JobSpy search boards, eleven API/feed sources, four opt-in scrapers, and eight public ATS adapters. The execution model is a Postgres-backed task queue that fetches and normalizes jobs, writes a global posting plus a per-user match, expires old records, and then queues ranking; however, Workday and arbitrary company career sites are not implemented.

- The code does not document how many real employers in the intended watchlist use each ATS, so the incremental coverage benefit of adding Workday cannot be quantified from the repository.
- There is no stored production yield/cost history per source, so the audit cannot rank sources by observed jobs per request, success rate, or downstream shortlist rate.
- Live source status is not established by this audit. The repository has manual live-smoke scripts, but they are intentionally excluded from pytest and require network access. — [live_smoke_sources.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/tests/fetchers/live_smoke_sources.py:1); [live_smoke.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/tests/fetchers/live_smoke.py:1)

## How are deduplication, freshness, and job quality handled today?

### Takeaway
The implementation has useful normalization, title/remote filters, recency controls, failure isolation, and a cheap-first ranking handoff. Its central weakness is that a single lossy hash is treated as both cross-source identity and the sole canonical record, so it can merge distinct requisitions, split equivalent jobs, and permanently preserve the first low-quality source representation.

### Cited Findings

#### Deduplication and canonicalization

- The dedupe key is SHA-1 of normalized company, normalized title, and normalized first location component. It does not include source, external ID, URL, requisition ID, posting date, or employment type. — [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:114)
- Company normalization removes accents, punctuation, parentheses, leading “The,” and many trailing legal/geographic suffixes; title normalization handles a small synonym set; location normalization maps selected city aliases and generally keeps only the first component. — [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:23); [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:64); [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:76); [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:94)
- In-batch duplicates keep the first posting unless a later record has a better two-bit score consisting only of “has description” and “has minimum salary.” There is no direct-source preference, description-length comparison, URL quality check, or freshness tie-breaker. — [fetchers/__init__.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/__init__.py:58)
- Database conflicts update `last_seen_at` and `is_active`, but preserve the original source, external ID, URL, title, company, location, raw payload, and any already-populated description. Salary is replaced only when both stored salary bounds are null, and `posted_at` is replaced only when null. — [jobs_db.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/jobs_db.py:87)
- The tests explicitly validate that a LinkedIn and Naukri representation of the same normalized company/title/location collide, and that reruns enrich missing description/salary without creating another posting. — [test_models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/tests/fetchers/test_models.py:18); [test_fetch_jobs.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/tests/test_fetch_jobs.py:138)
- One match can point to only one `search_id`; if the same user receives the posting from a second saved search, the conflict path does not record the second search because uniqueness is `(user_id, job_posting_id)` and the update only revives expired status. — [20250101000017_job_search.sql](/Users/himanshurawat/Desktop/Projects/orbithire/supabase/migrations/20250101000017_job_search.sql:82); [jobs_db.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/jobs_db.py:113)

### Inferences

- False merges are possible when one employer has multiple active requisitions with the same normalized title and first location; false splits are possible when equivalent jobs differ in title tokens or location formatting not covered by the small alias/replacement sets. — [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:31); [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:52); [models.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/models.py:131)
- Because database upsert preserves the first source identity and URL, an aggregator result that arrives first can permanently remain the displayed canonical record even after the direct ATS version appears; the direct source then only has a chance to fill missing description or salary. — [jobs_db.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/jobs_db.py:87)
- `last_seen_at` represents observation of the shared hash, not observation by a particular source or board. It therefore cannot support source-specific closure detection, provenance, or confidence in whether the direct employer listing is still live. — [20250101000017_job_search.sql](/Users/himanshurawat/Desktop/Projects/orbithire/supabase/migrations/20250101000017_job_search.sql:50); [jobs_db.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/jobs_db.py:96)
- Daily polling plus a 14-day absence threshold favors low request volume, but it is not “latest jobs” behavior: a newly published role may wait nearly a day to enter the inbox, and a closed role may remain active for two weeks. — [20250101000020_job_fetch_cron.sql](/Users/himanshurawat/Desktop/Projects/orbithire/supabase/migrations/20250101000020_job_fetch_cron.sql:83); [jobs_db.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/jobs_db.py:20)
- Allowing unknown-date feed records through protects recall but lets stale jobs bypass the declared `hours_old` promise. — [sources/base.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/fetchers/sources/base.py:113)

### Gaps

- There is no precision/recall evaluation set for the dedupe hash, so its false-merge and false-split rates are unknown.
- There is no recorded source provenance history after canonical upsert, so one cannot audit which sources agreed on a job or recover a later, better URL/raw payload.
- There is no URL liveness check, explicit employment-type validation, staffing/spam classifier, description-completeness threshold, or future-date sanity check in the ingestion path.
- There is no source-specific service-level objective for “published-to-ingested” delay or “closed-to-expired” delay.

## What operational, schema, and test gaps limit a low-cost production strategy?

### Takeaway
The code is defensive and well unit-tested at adapter boundaries, but it lacks persistent source telemetry, shared fetch caching, automated live-contract monitoring, and a canonical schema snapshot. These omissions make it hard to know which free sources are healthy and valuable, and cause avoidable duplicate upstream traffic as usage grows.

### Cited Findings

- Source results expose raw count, kept count, errors, skips, filtered count, and duplicate count only in the completed task result/logging path. The data model contains no `source_runs`, source health, request count, response latency, or downstream conversion table. — [fetch_jobs.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/handlers/fetch_jobs.py:152); [fetch_jobs.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/handlers/fetch_jobs.py:168); [20250101000017_job_search.sql](/Users/himanshurawat/Desktop/Projects/orbithire/supabase/migrations/20250101000017_job_search.sql:46)
- The worker health endpoint reports database state, process counters, and slot usage, but not source-level success, latency, block rate, last successful fetch, or yield. — [worker.py](/Users/himanshurawat/Desktop/Projects/orbithire/worker/orbithire_worker/worker.py:271)

## What concrete changes would improve freshness and quality at the lowest sustainable cost?

### Takeaway
Prioritize direct employer feeds, shared fetches, provenance-aware canonicalization, and measured source selection before buying more data. The first implementation tranche should add Workday plus a source-observation model, centralize duplicate upstream work, and instrument yield/quality; broad custom-site scraping should remain a narrow fallback.
