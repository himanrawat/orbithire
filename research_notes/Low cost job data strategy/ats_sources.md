# First-party ATS and company career feeds

## Which ATS sources can be fetched at low or zero marginal data cost?

### Takeaway
The best zero-key sources are first-party, employer-scoped feeds deliberately exposed to power public career pages. Greenhouse, Lever, Ashby, SmartRecruiters, Workable, Personio and Teamtailor all have documented public retrieval paths. — [Greenhouse](https://docs.greenhouse.io/job-board.html); [Lever](https://github.com/lever/postings-api); [Ashby](https://developers.ashbyhq.com/docs/public-job-posting-api); [SmartRecruiters](https://developers.smartrecruiters.com/docs/authentication); [Workable](https://help.workable.com/hc/en-us/articles/115012771647-Using-the-Workable-API-to-create-a-careers-page); [Personio](https://support.personio.de/hc/en-us/articles/29375445597725-Frequently-asked-questions-on-XML-job-integration); [Teamtailor](https://support.teamtailor.com/en/articles/11171756-rss-feed-how-to-guide) Recruitee is still anonymously reachable in October 2026 but has announced mandatory per-company tokens for its Careers Site API from 10 February 2027, while its XML feed remains outside that token requirement. — [Recruitee authentication](https://docs.recruitee.com/reference/authentication-1)

### Cited Findings
- **Greenhouse — top tier.** `GET https://boards-api.greenhouse.io/v1/boards/{board_token}/jobs?content=true` returns all published job posts; `content=true` adds the full description, departments and offices. GET endpoints require no authentication. The list includes a stable posting `id`, `updated_at`, requisition ID, canonical job URL, language and optionally exposed metadata; a per-job request adds `first_published` and `application_deadline`. The official documentation shows no pagination parameter for the jobs list, so one request retrieves the board. — [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html)
- **Lever — top tier, but weak timestamps.** `GET https://api.lever.co/v0/postings/{site}?mode=json` (or the EU host) returns public `published` postings and supports `skip`/`limit` plus location, commitment, team, department and level filters. Records include stable ID, title, location/category data, plain and HTML descriptions, hosted/apply URLs, workplace type and optional salary. Lever explicitly says published postings are publicly viewable and may be scraped by third parties, but the documented posting object has no publication or update timestamp. — [Lever Postings API](https://github.com/lever/postings-api)
- **Ashby — top tier and especially rich.** `GET https://api.ashbyhq.com/posting-api/job-board/{board}?includeCompensation=true` returns all currently published postings in one JSON response, with title, primary and secondary structured locations, team, department, remote/workplace type, HTML and plain descriptions, `publishedAt`, employment type, job/apply URLs and optional structured compensation. No credential is shown in the documented request. — [Ashby Job Postings API](https://developers.ashbyhq.com/docs/public-job-posting-api)
- **SmartRecruiters — top tier.** `GET https://api.smartrecruiters.com/v1/companies/{companyIdentifier}/postings?limit={limit}&offset={offset}` lists active postings and supports query and location/department filters; a detail request returns the full posting. The public Posting API is one of the APIs explicitly available without authentication, and list responses include `releasedDate`, `totalFound`, `limit` and `offset`. SmartRecruiters documents a general Customer API ceiling of 10 requests/second and eight concurrent requests. — [Posting endpoints](https://developers.smartrecruiters.com/docs/endpoints); [authentication](https://developers.smartrecruiters.com/docs/authentication); [API overview and throttling](https://developers.smartrecruiters.com/docs/customer-overview)
- **Workable — useful supported public options, with tradeoffs.** Workable officially documents anonymous company endpoints such as `https://www.workable.com/api/accounts/{account_subdomain}?details=true` for published jobs, plus locations and departments endpoints. Its authenticated SPI v3 API requires a Super Admin-created token with `r_jobs`, so it is unsuitable for collecting arbitrary employers without cooperation. Workable also publishes a global XML feed at `https://www.workable.com/boards/workable.xml`; that feed contains all customers' jobs approved and published to Jobs by Workable, is refreshed hourly, cannot be filtered server-side and must be downloaded in full. — [Workable careers API guide](https://help.workable.com/hc/en-us/articles/115012771647-Using-the-Workable-API-to-create-a-careers-page); [Workable XML feed](https://help.workable.com/hc/en-us/articles/4420464031767-Utilizing-the-XML-Job-Feed)
- **Recruitee — use the XML feed for durability.** The current public endpoint `GET https://{company}.recruitee.com/api/offers/` returns published jobs and can filter by department or tag; Recruitee also documents formatted XML (`/api/feeds/offers.xml`), raw XML (`/api/offers.xml`) and JSON (`/api/offers`) feeds. However, Recruitee states that Careers Site API calls without `X-Careers-Sites-Token` will return `401` after 10 February 2027; the XML offer feed and jobs widget are explicitly not covered by the Careers API token. — [Recruitee offers endpoint](https://docs.recruitee.com/reference/offers); [Recruitee authentication transition](https://docs.recruitee.com/reference/authentication-1); [Recruitee feed FAQ](https://support.recruitee.com/en/articles/8213076-faq-api)
- **Teamtailor — strong public RSS fallback.** Adding `.rss` to a Teamtailor careers jobs page, for example `https://career.teamtailor.com/jobs.rss`, yields public metadata including title, description, publication date, URL, remote status, global ID, locations, department, role and division. It defaults to 100 jobs and supports `offset` and `per_page`. — [Teamtailor RSS guide](https://support.teamtailor.com/en/articles/11171756-rss-feed-how-to-guide)
- **Personio — strong XML feed, moderate schema richness.** `GET https://{account}.jobs.personio.com/xml?language=en` is credential-free when the employer enables the feed. Personio recommends syncing at least hourly and says the feed updates when job attributes change. The documented XML contains ID, subcompany, office, department, category, title, HTML description blocks, employment type, seniority, schedule, experience range, keywords, occupation and `createdAt`; it supports several language variants. — [Personio XML FAQ](https://support.personio.de/hc/en-us/articles/29375445597725-Frequently-asked-questions-on-XML-job-integration); [Personio XML schema](https://developer.personio.de/docs/retrieving-open-job-positions)
- **Public does not automatically mean unrestricted commercial reuse.** These endpoints are documented primarily to let an ATS customer populate its own careers site. Except for Lever's unusually explicit statement that published postings may be scraped, the reviewed product documentation does not itself grant a blanket license to aggregate and republish every customer's data. — [Greenhouse purpose statement](https://docs.greenhouse.io/job-board.html); [Ashby purpose statement](https://developers.ashbyhq.com/docs/public-job-posting-api); [Lever Postings API](https://github.com/lever/postings-api)

### Inferences
- For a low-cost product, implement Greenhouse, Ashby, Lever and SmartRecruiters first: they offer the cleanest structured data, stable company-scoped identifiers and direct apply URLs with little or no HTML parsing.
- Add Personio and Teamtailor next via XML/RSS. These feeds are intentionally machine-readable and cheap to poll, but normalization work is higher and some fields are less structured.
- Prefer Workable's employer-scoped anonymous endpoint for targeted companies; use its global hourly XML feed only as discovery/backfill because downloading the entire unfilterable feed is bandwidth-heavy and excludes jobs not approved/published to Jobs by Workable.
- For Recruitee, build the XML path as the default now rather than shipping a JSON integration that is known to require employer-issued tokens in February 2027.
- Treat “no authentication” as a technical access fact, not legal clearance. Store source URL, employer, fetch time and terms/robots audit status, and obtain counsel for the intended commercial use.

### Gaps
- Greenhouse, Lever, Ashby, Workable's anonymous company endpoint, Personio and Teamtailor do not publish a retrieval rate limit in the reviewed pages. Use conservative per-host throttling, jitter, backoff on `429`/`503`, and conditional requests when the origin supports them.
- The official docs do not guarantee propagation latency for most board feeds. Freshness should therefore be measured empirically per source and employer.
- Some employers can use custom domains or disable optional feeds, so board discovery must tolerate missing feeds and verify candidates before scheduling recurring polls.

## What is the safest and most reliable Workday strategy?

### Takeaway
Workday's career UI uses an unauthenticated CXS JSON endpoint, yet that endpoint is undocumented, tenant-specific and unsupported. — [Community Workday source guide](https://github.com/Francis1998/agentic-career-search/blob/main/docs/guides/WORKDAY_SOURCE_GUIDE.md) Workday's published site terms prohibit data mining/scraping and applications that interact with its sites without prior written consent. — [Workday Terms of Service](https://www.workday.com/en-us/legal/site-terms.html) Therefore, use employer-owned job sitemaps or structured pages first, and enable CXS only for an allowlisted employer/source after a terms review or permission.

### Cited Findings
- Community implementations consistently identify the list route as `POST https://{tenant}.wd{N}.myworkdayjobs.com/wday/cxs/{tenant}/{site}/jobs` with a JSON body containing `appliedFacets`, `limit`, `offset` and `searchText`; the career-site URL is needed to discover the exact tenant, shard and site because these cannot be safely derived from company name alone. — [Open-source Workday source guide](https://github.com/Francis1998/agentic-career-search/blob/main/docs/guides/WORKDAY_SOURCE_GUIDE.md); [technical reference with a live-tested example](https://conorscode.github.io/ats-api-reference/)
- The observed CXS list endpoint has a hard page size of 20; full descriptions require a per-job detail GET using the returned `externalPath`. The list result exposes a total and summary fields, while the detail response adds HTML description and more location/time information. These behaviors are community-verified, not covered by an official Workday public API contract. — [Open-source Workday source guide](https://github.com/Francis1998/agentic-career-search/blob/main/docs/guides/WORKDAY_SOURCE_GUIDE.md); [ATS API reference](https://conorscode.github.io/ats-api-reference/)
- Workday's terms state that its covered Sites include Workday APIs and prohibit scraping/data-mining methods, reverse engineering, bypassing access controls or `robots.txt`, and developing applications that interact with the Sites without prior written consent. — [Workday Terms of Service](https://www.workday.com/en-us/legal/site-terms.html)
- Workday itself tells candidates who doubt a job's validity to apply directly through the employer/Workday careers website, reinforcing first-party career pages as the authenticity source. — [Workday careers](https://www.workday.com/en-us/company/careers/overview.html)
- Workday offers customer-controlled integration products that can generate XML output containing active postings for delivery to an external endpoint, but that is a cooperative employer integration rather than a universal public feed. — [Workday Integration Cloud datasheet](https://www.workday.com/content/dam/web/en-us/documents/datasheets/workday-integration-cloud-connectors-hcml-datasheet.pdf)

### Inferences
- Discovery should start from the company's own careers link, not tenant/shard probing. Parse and persist `{origin, tenant, site, locale}` only after the company page links to the Workday board.
- Recommended fetch sequence: (1) look for a company/Workday sitemap and per-job `JobPosting`; (2) if permission and terms review allow CXS, POST list pages at a slow cadence with `limit:20`; (3) fetch detail only for new or changed `externalPath` values; (4) mark removals only after two or more misses to avoid transient false closures.
- Use a per-board lock, low concurrency, exponential backoff and a circuit breaker on `403`, `429`, CAPTCHA or schema changes. Never evade controls, rotate identities to bypass limits, or probe datacenters/site slugs.
- Workday list freshness fields are inconsistent (often relative display text), so record `first_seen_at`, `last_seen_at`, response fingerprints and HTTP fetch time. Treat any extracted posting date as source-supplied display metadata, not a universally comparable timestamp.
- If legal certainty is required, ask employers to provide their Workday XML/outbound feed or written authorization. That converts an unstable scrape-like integration into a supported data relationship.

### Gaps
- Workday provides no public official documentation, SLA, rate limit, versioning guarantee or license for the CXS career endpoint in the reviewed sources.
- The applicability of Workday's site terms versus an individual employer's own terms can depend on host, contract and jurisdiction. This report is technical research, not legal advice.
- Anti-bot behavior and response shapes can vary by tenant and may change without notice; live monitoring and fast disablement are required.

## How should company-hosted career pages, JobPosting markup and sitemaps be used?

### Takeaway
Google's job-search guidance treats the canonical, single-job detail page as the correct home for `JobPosting` data and recommends accurate sitemap/RSS/Atom modification times for job URL discovery. — [Google JobPosting documentation](https://developers.google.com/search/docs/appearance/structured-data/job-posting) Accordingly, use job-specific sitemaps/RSS/Atom for discovery and change detection, then extract `schema.org/JobPosting` JSON-LD from the canonical detail page; fall back to DOM parsing only when structured data is absent and the site's terms and robots rules permit it.

### Cited Findings
- Google requires job structured data to appear on the same page as a single visible job description and recommends canonical URLs for duplicate copies. Required/recommended fields include the original `datePosted`, full `description`, hiring organization, job location and other job-specific properties. — [Google JobPosting documentation](https://developers.google.com/search/docs/appearance/structured-data/job-posting)
- Schema.org defines reusable fields including `datePosted`, `directApply`, `baseSalary`, education requirements and eligibility-to-work requirements. — [Schema.org JobPosting](https://schema.org/JobPosting)
- Google recommends the Indexing API for faster notifications from site owners but still recommends a sitemap for complete coverage. For job sitemaps, canonical detail URLs should be included, and accurate `lastmod`/RSS `pubDate`/Atom `updated` values should reflect real content changes; search/list pages should not be included. — [Google JobPosting documentation](https://developers.google.com/search/docs/appearance/structured-data/job-posting)
- Google says expired jobs should be removed via a past `validThrough`, a `404`/`410`, or removal of the `JobPosting` markup; stale expired postings can trigger manual action. — [Google JobPosting documentation](https://developers.google.com/search/docs/appearance/structured-data/job-posting)
- Google notes that publishing does not imply immediate discovery: crawling/re-indexing can take days. Therefore Google search results are useful for discovery but are not as fresh as direct employer polling. — [Google JobPosting documentation](https://developers.google.com/search/docs/appearance/structured-data/job-posting)

### Inferences
- Build a domain-scoped discovery ladder: explicit ATS URL -> `robots.txt` sitemap declarations -> `/sitemap.xml` and sitemap indexes -> career-specific XML/RSS/Atom -> internal career links. Prioritize URLs whose path and structured data indicate one job per page.
- Validate JSON-LD against the visible page and canonical URL. Reject list-page markup, expired `validThrough`, missing apply path, mismatched employer, and pages returning soft-404 content.
- For freshness, combine source timestamps with observations: `source_date_posted`, `source_date_modified`, `first_seen_at`, `last_seen_at`, `closed_at`, content hash and last successful HTTP status. A source timestamp must never be silently replaced by crawl time.
- Poll sitemap/feed metadata first, then fetch only new or changed detail URLs. This is much cheaper than repeatedly rendering every career page and makes closed-job detection more reliable.
- Keep direct employer URLs as the canonical record and ATS/aggregator URLs as aliases. This improves authenticity, deduplication and user trust.

### Gaps
- Many sites omit structured data, misuse `datePosted`, never set `validThrough`, or update `<lastmod>` on template changes. Source-level trust scores and anomaly checks are necessary.
- Sitemaps disclose URLs, not necessarily complete job content, and some JavaScript sites require rendering. Rendering cost should be reserved for high-value allowlisted companies after static HTML and embedded JSON checks fail.

## Why should Glassdoor and LinkedIn not be primary acquisition sources?

### Takeaway
Direct automated collection from Glassdoor or LinkedIn is a poor low-cost foundation because both explicitly restrict unapproved scraping. — [LinkedIn Crawling Terms](https://www.linkedin.com/legal/crawling-terms); [Glassdoor Terms of Use](https://www.glassdoor.com/about/terms-2022-12-01/) Use them only through an approved API, partner agreement or human-facing outbound links; get the actual job from the employer or its ATS.

### Cited Findings
- LinkedIn's crawling terms say automated crawling/indexing without express permission is strictly prohibited and direct applicants to request permission; approved crawlers must follow authorized paths and robots restrictions and may not use collected data in a competitive service or transfer it in bulk. — [LinkedIn Crawling Terms](https://www.linkedin.com/legal/crawling-terms)
- LinkedIn's help center says it does not permit third-party crawlers, bots, browser plugins or extensions that scrape or automate activity on LinkedIn, and identifies these as violations of its User Agreement. — [LinkedIn prohibited software guidance](https://www.linkedin.com/help/linkedin/answer/a1341387/prohibition-of-scraping-software)
- LinkedIn's API terms also prohibit accessing or facilitating content obtained by scraping/crawling outside its APIs and restrict aggregation of API content with third-party data where attribution is lost. — [LinkedIn API Terms](https://www.linkedin.com/legal/l/api-terms-of-use)
- Glassdoor's terms prohibit introducing automated agents to scrape, strip or mine its services without express written permission, prohibit framing/deep-linking except via formal features, and restrict using its content in a competitive service. — [Glassdoor Terms of Use](https://www.glassdoor.com/about/terms-2022-12-01/)

### Inferences
- Even if these sites expose technically reachable data, proxies, browser automation and CAPTCHA-solving increase both cash cost and compliance risk while producing less authoritative freshness than the originating employer feed.
- Treat a LinkedIn or Glassdoor job URL as a discovery hint only. Resolve it to the employer/ATS canonical posting before ingesting; never copy reviews, salaries or job text from those platforms without an approved license.
- Do not buy third-party datasets that claim LinkedIn/Glassdoor provenance unless the vendor can document authorized acquisition and redistribution rights.

### Gaps
- Approved commercial access, pricing and redistribution rights are contract-specific and are not publicly enumerated in the reviewed materials.
- Terms vary by jurisdiction and may change; production use needs periodic legal/terms review.

## Which sources provide the highest quality and latest postings, and how should they be prioritized?

### Takeaway
Rank first-party feeds by authenticity, machine readability and timestamp quality—not by nominal volume. Greenhouse, Ashby and SmartRecruiters expose explicit posting/update timestamps; Lever does not document one; Teamtailor and Personio expose publication/creation times; Workable's global XML is hourly. — [Greenhouse](https://docs.greenhouse.io/job-board.html); [Ashby](https://developers.ashbyhq.com/docs/public-job-posting-api); [SmartRecruiters](https://developers.smartrecruiters.com/docs/endpoints); [Lever](https://github.com/lever/postings-api); [Teamtailor](https://support.teamtailor.com/en/articles/11171756-rss-feed-how-to-guide); [Personio](https://developer.personio.de/docs/retrieving-open-job-positions); [Workable](https://help.workable.com/hc/en-us/articles/4420464031767-Utilizing-the-XML-Job-Feed) A practical order is therefore: Greenhouse/Ashby/SmartRecruiters; Lever; Teamtailor/Personio; Workable; Recruitee XML; company sitemap plus `JobPosting`; and finally permissioned Workday. Polling should be adaptive, with faster cadence for priority companies and slower cadence for quiet boards.

### Cited Findings
- Greenhouse exposes `updated_at` in the list and `first_published` plus an application deadline on detail, making it strong for both change detection and ranking by recency. — [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html)
- Ashby includes a normalized ISO `publishedAt` together with rich location, remote, employment and optional compensation fields in a single response. — [Ashby Job Postings API](https://developers.ashbyhq.com/docs/public-job-posting-api)
- SmartRecruiters lists `releasedDate`, supports offset pagination and says posting content is a snapshot of the last time the job was published; content changes require re-posting. — [SmartRecruiters endpoints](https://developers.smartrecruiters.com/docs/endpoints); [Customer API overview](https://developers.smartrecruiters.com/docs/customer-overview)
- Lever supplies excellent descriptions, workplace type, location and optional salary but no documented publication/update timestamp, so a collector must establish freshness through observation. — [Lever Postings API](https://github.com/lever/postings-api)
- Teamtailor RSS includes publication date and structured organizational metadata; Personio XML includes `createdAt` and recommends at least hourly synchronization. — [Teamtailor RSS guide](https://support.teamtailor.com/en/articles/11171756-rss-feed-how-to-guide); [Personio XML schema](https://developer.personio.de/docs/retrieving-open-job-positions); [Personio XML FAQ](https://support.personio.de/hc/en-us/articles/29375445597725-Frequently-asked-questions-on-XML-job-integration)
- Workable's global XML feed is updated hourly, placing a hard practical ceiling on freshness through that route. — [Workable XML feed](https://help.workable.com/hc/en-us/articles/4420464031767-Utilizing-the-XML-Job-Feed)

### Inferences
- **Quality scoring:** award the highest provenance score to an employer-owned canonical page or documented ATS feed linked by the employer. Lower the score for custom scraped HTML, unverified redirects, missing apply links, or conflicting employer identity.
- **Freshness scoring:** keep both source time and observation time. Rank by reliable `first_published`/`publishedAt`/`releasedDate` when present; for Lever and Workday, rank by `first_seen_at` and clearly label it “discovered,” not “posted.”
- **Polling:** start a newly added board at 15–30 minutes, learn its posting/change frequency, then relax quiet boards to 2–6 hours. Personio and the Workable global XML feed gain little from sub-hour polling because their own guidance/feed cadence is hourly.
- **Incremental work:** poll one board list/feed, fingerprint normalized records, fetch details only for new/changed jobs, and close records after confirmed disappearance. This yields low request and compute costs without paying an aggregator.
- **Deduplication:** prefer ATS posting ID plus board ID as the primary key; add canonical URL, employer domain, requisition ID, normalized title/location and description fingerprint for cross-source merges. Do not merge solely on title and company.
- **Operational recommendation:** ship documented no-key adapters first, add a generic sitemap/JSON-LD adapter, and keep Workday behind an explicit feature flag and allowlist. This maximizes high-quality coverage while containing the only source with both unsupported mechanics and an explicit terms concern.

### Gaps
- No public source gives a complete universe of employer career pages; company discovery remains a separate problem.
- “Latest” cannot be guaranteed when employers backdate, repost, edit silently or delay feed publication. The system should expose provenance and observed times rather than promise a universally correct posting date.
- The suggested polling intervals are engineering recommendations inferred from source characteristics, not vendor SLAs.
